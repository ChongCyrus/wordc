# 0.11.0 原生 SQLite 主库重构架构方案

## 0.1 Lead 拍板（2026-11-23）

- **A**：words/decks/packs 不进 SQLite，保持 assets→IDB 可重建缓存；但启动必须先确保 words 就绪，再读 SQLite facts。
- **B**：JavaBridge 一律异步：native 后台线程/Executor 执行 SQLite，JS 侧 Promise/回调（requestId + `__momoSqliteResult`），禁止 UI 线程同步磁盘事务。
- **C**：升级 0.11 前必须成功完整备份；保留 0.10.0 APK 回退；迁移前弹窗说明。
- **不用 Room**：手工 javac/d8 构建，无 Gradle/kapt/annotationProcessor；使用 framework `SQLiteOpenHelper` + 手写 SQL/事务，无第三方依赖；`PRAGMA journal_mode=WAL`、`synchronous=FULL`。
- **降级保护**：`user_version` 高于当前 App → `onDowngrade` 拒绝打开/写入，进入只读恢复页；IDB cache `dirty` 时读一律回源 SQLite。

状态：设计稿（0.10.0 源码保留回退）；不写实现代码，不改 API。

## 1. 目标与边界

### 目标
- APK 内 **Android framework SQLiteOpenHelper + WAL SQLite 为唯一事实源（single source of truth）**。
- 学习状态（states/plans/settings/reviewLogs/diag）只写 SQLite（**不用 Room**：构建为手工 javac/d8，无 Gradle/注解处理）；IndexedDB 降级为**可随时重建的读缓存**。
- 评分/计划事务在 SQLite 原子提交；进程被杀、WebView 回收、磁盘异常均不丢已提交状态。
- 0.9/0.10 用户数据一次性迁移；失败可回滚到旧 IndexedDB（保留 0.10.0 回退包）。
- 保持现有 App UI 数据接口语义：data 层加 SQLite repository，UI 尽量少改。

### 非目标
- 不在 0.11.0 合并 words/packs 静态词库进 SQLite（词库仍来自 assets/内容包，IndexedDB 可重建；如需搜索性能另立期）。
- 不改变 DHP 算法/计划状态机语义。
- 不引入云同步。

## 2. 分层

```
UI
 └─ data repository（保留现有函数签名）
     ├─ NativeSqliteStore（JSON-RPC over MomoBridge）
     │    └─ SQLiteOpenHelper + 手写 SQL/WAL（唯一事实源）
     └─ IdbCache（Dexie）
          ├─ states/plans/settings/reviewLogs 只读缓存
          ├─ words/decks/packs 可重建缓存
          └─ cacheMeta: sqliteVersion, rebuiltAt, generation, dirty
```

规则：
1. **写**：SQLite 事务成功 → 更新/失效 IDB cache → 才向 UI 返回成功。
2. **读**：优先 IDB cache（快）；cache generation 与 SQLite 不一致时阻塞重建/回源查询。
3. cache 写失败只标记 `dirty=true`，不回滚 SQLite；下次启动/前台重建。
4. 任何 UI 不得直接写 Dexie 学习表（0.11.0 后逐步封禁）。

## 3. SQLite schema（手写 DDL）

数据库：`momo.db`，**WAL=ON**，`synchronous=FULL`，`foreign_keys=ON`，`busy_timeout=5000`。
`SQLiteOpenHelper` 手写 `onCreate/onUpgrade/onDowngrade`；`PRAGMA user_version` 管 schema 版本。
**降级保护**：`onDowngrade` 不删库——若 `oldVersion > newVersion` 抛 `SQLiteException` 并进入只读恢复模式，禁止低版本 APK 打开高版本库。

## 4. 桥接 API（JS ↔ Native）

> 决策：JavaBridge **必须异步**。原生在后台单线程/Executor 执行 SQLite，`MomoBridge` 方法立即返回 requestId，结果通过 JS Promise 回调。
> 禁止在 WebView UI 线程做磁盘事务；JS 侧封装 `sqliteCall(op)` 返回 Promise。

SQLite 操作用**批量 JSON-RPC**，单次 native 调用内完成事务，避免跨线程多次往返：

```ts
// native 方法立即返回 requestId；结果通过 window.__momoSqliteResult(reqId, json) 回到 Promise
interface SqliteBridge {
  sqliteCall(reqJson: string): string // {"requestId":"..."} | {"error":"E_UNSUPPORTED"}
  sqliteCancel(requestId: string): string
}

// JS 侧
sqliteCall({
  id: 'uuid',
  method: 'health' | 'query' | 'exec' | 'tx' | 'backup' | 'integrity',
  tx?: true,
  ops?: Op[],
  expect?: { userVersion?: number; dataEpoch?: number },
  timeoutMs?: number,
  maxBytes?: number
}): Promise<SqliteResponse>
```

请求示例：
```json
{
  "id": "uuid",
  "tx": true,
  "ops": [
    {"op":"upsert","table":"states","rows":[...]},
    {"op":"insert","table":"review_logs","row":{...}},
    {"op":"update","table":"plans","where":{"id":"..."},"patch":{...}}
  ],
  "expect": {"dataEpoch": 12},
  "maxBytes": 8388608
}
```

响应：
```json
{"ok":true,"changes":3,"dataEpoch":13,"durationMs":4}
```
错误码：`E_BUSY/E_IO/E_QUOTA/E_SCHEMA/E_CONFLICT/E_TOO_LARGE/E_CORRUPT/E_UNSUPPORTED/E_ABORTED`。
- 表白名单：states/plans/settings/review_logs/diag/schema_meta/migration_state（native 拒绝其他表）。
- query：`{rows: Row[], columns:[{name,type:'TEXT'|'INTEGER'|'REAL'|'BLOB'|'NULL',notNull?,primaryKey?}], nextCursor}`，行字段为 JSON 标量/JSON 字符串。
- backup：`{ok:true,path,bytes,at}`（失败 `{ok:false,code,message}`）。
- 错误：顶层 `{ok:false,code,message,error?}`；JS 统一抛 `SqliteError(code,message)`。
- 禁止 SQL 字符串拼接；JS 只传结构化 op，原生用 SQLiteOpenHelper `beginTransaction/setTransactionSuccessful/endTransaction`。
- 单次返回值/入参上限 8MB，超过由 data 层分片；查询分页 `limit/afterId`。
- 不支持回读不可序列化对象；所有字段 JSON。
- 原生结果回调必须在主线程/Handler 切回 JS；超时由 JS 侧拒绝并 `sqliteCancel`。

### 暂停/取消
- 长操作带 `opId`，bridge 暴露 `sqliteCancel(opId)`；每个写批次检查取消/epoch。
- 事务失败/取消 → native rollback + 返回错误；JS 不重试有副作用的写。

## 5. 启动重建 IndexedDB 流程

启动顺序（APK）：
1. 检查 `MomoBridge.sqliteHealth()`；不可用/失败 → 记录 diag，进入 **安全只读/恢复模式**（不自动清空）。
2. 若 SQLite 空：
   - 若存在旧 IDB（0.9/0.10）→ 执行一次性迁移（见 §6）。
   - 否则全新库：从 assets 种子词库/内容包（现有 ensureBuiltinDecks），写 settings 默认。
3. 校验/修复 IDB cache：
   - 比较 `cacheMeta.generation` 与 SQLite `schema_meta.idb_cache_generation`；
   - 不一致/缺失/dirty → 按分页从 SQLite 拉 states/plans/settings/reviewLogs 重建（words/packs 由 assets 重建）。
   - 重建在后台分片，先标记 cache `rebuilding`，UI 读走 SQLite 回源或等待。
4. 构建完成后 `cacheMeta.rebuiltAt=now, generation=...`；首页才显示数据。
5. checkpoint/auto-backup 仍作为二级备份；恢复流程改为先恢复 SQLite，再重建 IDB cache。

关键：**IDB 丢失只影响启动速度，不影响事实数据**；IDB 损坏时直接删库重建（words 也重建）。

### dirty / 读写回源
- IDB cache 标记 `dirty=true`（写 cache 失败/进程杀/版本不一致）时：
  - 写路径照常 SQLite 优先；
  - 读路径对脏表**回源 SQLite**（分页/单行），不得把 stale cache 当事实；
  - 后台按 generation 重建，完成后清 dirty。
- 重建期间新评分：SQLite 提交成功后，若 cache 仍重建中，写入 `cache_outbox`（或下次全量重建）；不阻塞评分。

## 6. 0.9/0.10 → 0.11 迁移

### 前置
- **升级前强制完整备份**（0.10.0 auto backup/迁移前 VACUUM INTO）；未成功则拒绝升级/迁移。
- 保留 0.10.0 回退 APK；回退需从升级前备份恢复（0.10 不能读 SQLite）。
- 迁移只在 `schema_meta.migrated_from` 为空时执行一次。
- 全程持有原生迁移锁 + `migration_state`。

### 步骤
1. 读取旧 IDB：states/plans/settings/reviewLogs（**不含 words**，words 由当前 assets 重建）。
2. 按现有 schema 校验：
   - states 去重 wordId，基础字段 clamp；preserve `meaningStats/coreSenseStats/partStats` JSON；
   - plans 逐条 wordIds/sources/ratings 校验，缺失词标记并压缩（调用统一 helper 语义）；
   - settings 按 SETTING_KEYS 校验，未知键保留但不读取；
   - reviewLogs 逐条写，保留 id 冲突则重编号并记 diag；
   - legacy sources 归一化（goal/extra/requeue/manual/random/order）。
3. 单事务批量写入 SQLite（每批 ≤500 行）；写 `migration_state` step。
4. 成功后写 `schema_meta.migrated_from='0.10.0'`, `data_epoch+1`, `idb_cache_generation` 失效 → 重建 IDB cache。
5. 校验：迁移前后 counts（states/plans/settings/reviewLogs）一致；抽样 wordId 状态一致；失败则 **不标记完成**，下次重试。

### 回滚
- 迁移失败：SQLite 事务回滚，IDB 原数据保持可读；App 回退 0.10.0 包仍可启动。
- 迁移成功但发布回滚：0.10.0 无法读 SQLite，需保留 0.10.0 前自动备份；升级流程弹窗提示「回退包需从备份恢复」。
- SQLite 损坏：`PRAGMA integrity_check` 失败 → 进入恢复页，从 auto backup/checkpoint 恢复，不自动删库。

## 7. 写路径改造（示例）

`submitRating`：
1. data 层构建 `SqliteTxRequest`（states upsert、review_logs insert、plan update、diag）。
2. 调 bridge；成功返回 `{dataEpoch, changes}`。
3. 更新 IDB cache：states/plan/reviewLog 单事务（cache 失败只置 dirty）。
4. 评分成功后 schedule checkpoint（现有 2s）。

`ensureBuiltinDecks` / imports：
- words/packs 仍写 IDB/assets；学习事实变更（states/plans）走 SQLite diff 事务，删词同步 SQLite 引用清理。
- 全局写锁（现有 `withDataWriteLock`）+ native `data.epoch` 双保险。

## 8. 故障注入与验收

必须覆盖：
| 场景 | 期望 |
|---|---|
| bridge 返回 E_BUSY | 指数退避，限次；不丢已提交 |
| 迁移中 kill | 事务回滚/迁移未完成，下次重试；IDB 可读 |
| SQLite disk full/E_QUOTA | 写拒绝，事务回滚；UI 提示清理；不损坏旧数据 |
| WAL 损坏 / integrity_check fail | 只读恢复模式 + 恢复入口；不自动清库 |
| IDB cache 损坏/丢失 | 从 SQLite 重建，进度不丢 |
| 恢复/导入中断 | SQLite 事务回滚，旧数据保留 |
| 并发评分+seed/import | 全局锁/epoch 串行，计数一致 |
| 25MB 备份恢复 | 迁移/恢复后 counts 一致，强杀可继续 |
| 0KB/坏备份 | 不在可恢复列表；手动恢复拒绝 |

验收脚本（短）：迁移前后 counts、评分后 kill/重启、IDB 删除后重建、SQLite 只读/磁盘满注入。
长 soak/真机按发布前单独跑。

### 顺序约束（不可颠倒）
- **M3 必须在 M4 之前完成**：否则 M4 新评分写入 SQLite 后 counts>0，M2 readThrough 会标 dirty 回源 SQLite，而历史 240 states 仍在 IDB → 历史进度“消失”。
- M3 期间：写路径仍 IDB；读路径继续 cache（M2）；SQLite 只作为迁移目标，迁移完成后仍不切写。
- M3 完成校验：SQLite counts 与 IDB 迁移前 counts 一致；`schema_meta.migrated_from=0.10.0`，`migration_state` 全部 step=done，`data_epoch+1`；之后才允许 M4。
- M4 切写时 IDB cache 必须已由完整 SQLite 重建/校验（generation 一致、dirty=false），读回源不会丢历史。

## 12. 连接池 synchronous 决策（M1 真机发现）

真机 health 报 `synchronous=FULL(2)`，但 selfTest 的普通查询连接报 `synchronousValue=1/NORMAL`——Android `SQLiteDatabase` 连接池下 **PRAGMA synchronous 是每连接设置**，WAL 下新连接可能默认 NORMAL。

**决定：采用 WAL + writer 连接 `synchronous=FULL`，读连接允许 NORMAL；不再声称所有连接统一 FULL。**
- 写事务走主写连接；`MomoSqliteOpenHelper.onOpen` 对写连接显式 `PRAGMA synchronous=FULL`。
- `health` 同时输出 `connectionSynchronous`（当前读连接，可能 NORMAL）与 `synchronous/writeSynchronous`（写连接，必须 FULL）。
- `selfTest` 在写事务内读取 `writeSynchronous`，`ok` 要求 `writeSynchronous=FULL`；`checks` 同时含 `writeSynchronousValue`。
- 语义：WAL 下已提交事务在 `synchronous=FULL` 写连接上 fsync；读连接 NORMAL 只影响该连接读取，不影响已提交写可靠性。断电场景仍可能丢失**未提交**/最后未 fsync 事务，这不承诺。
- 验收：health 必须 `writeSynchronous=FULL`；若写连接也 NORMAL，M1 不通过（M2 前修复连接配置）。
- 未来若需全连接 FULL，可改用单连接配置/连接池反射，但不作为 M1 目标。

### M5 native 备份接口（2026-11-23 实现）

`sqliteCall({method:'backup', name?})` 返回 `{name,path,bytes,at,integrityOk}`；实现为：
1. `PRAGMA wal_checkpoint(FULL)`（有限重试）→ 复制 `momo.db` 到 `files/sqlite-backups/*.db.partial`；
2. 用只读 `SQLiteDatabase.openDatabase` 打开副本执行 `PRAGMA integrity_check`；
3. 0KB/校验失败删除 partial；成功 `.partial` rename 为正式名；不覆盖前先删除旧同名；
4. 返回 path/bytes/at/integrityOk。

说明：本机 android.jar API23 的 SQLite 不支持 `VACUUM INTO`（3.27+），因此采用 WAL checkpoint + 文件复制 + integrity_check；结果等价于一致性快照（复制期间由单线程 SQLite 执行器持有，无并发写）。备份文件是 **SQLite 文件**，不是 migration JSON；M5 自动备份需额外写 manifest（counts/epoch/userVersion/checksum），恢复时用 SQLite 文件替换/导入。

### M5 备份/检查点目录约定（2026-11-23，Lead 拍板）

- **SQLite facts `.db` 备份**：native `files/sqlite-backups/`；列表只经 native `listBackups`（`sqliteCall`），不用 `MomoBridge.list()`（auto 目录）；每个 `.db` 对应 IDB meta `sqliteBackup.manifest:<name>`（counts/bytes/checksum/epoch/userVersion/integrity），列表要求 size>0 + manifest.bytes 匹配 + integrityOk。
- **checkpoint JSON**：继续用 `AutoBackupBridge` 的 auto-backup 目录（native 私有），文件名 `sqlite-checkpoint-*.state.json`；它是**小 JSON 快照**，不混入 SQLite `.db` 列表；写/读/list/delete 同目录自洽。native 不新增 checkpoint API。
- 恢复：`file path → manifest → restoreSqliteFactsBackup({path,manifest})`；先 preBackup，native restoreDb 校验/备份旧库/失败回滚；恢复后 counts 与 manifest 对比。
